# installers/ — the npx and pip packages

Canonical **source** for the two published installers. Both are ports of `init.sh` with **fetch-first-with-fallback** template sourcing: at install time they fetch the current templates from GitHub main, and fall back to the copy **bundled at build time** if the fetch fails (offline, blocked, no system tar). Fresh when online, always works, and both paths place real files — the never-reconstruct rule holds everywhere. `--offline` / `ALLOSTATIK_OFFLINE=1` skips the fetch (legacy `ALLOSTAT_OFFLINE=1` accepted until 1.0).

- `npm/` — publishes as [`allostatik` on npm](https://www.npmjs.com/package/allostatik): `npx allostatik init ./your-project`
- `pip/` — publishes as [`allostatik` on PyPI](https://pypi.org/project/allostatik/): `pip install allostatik && allostatik init ./your-project`

**Templates are not stored here** — `scripts/bundle-templates.sh` copies `templates/project-boilerplate/` (plus `UPGRADING.md` and `CHANGELOG.md`, so the packages carry a second copy of the upgrade path for the routine's cross-check) into each package right before publishing. The canonical templates live in `templates/`; anything under `installers/npm/templates/` or `installers/pip/src/allostatik/templates/` is a gitignored publish artifact. (DRY: one source, assembled copies.)

**Behavior parity is a tested invariant.** `scripts/test-installers.sh` runs init.sh, the npm bin, and the pip CLI against identical scratch projects (greenfield, existing, collision, tool-repo-collision) and diffs the resulting trees and exit codes. Run it after touching any of the three.

**Releasing:**

1. **Sign in first — always, not conditionally.** The session has expired at every release so far, so checking and then signing in is a round trip that has never once come back clean. Run `npm login`, then confirm with `npm whoami`; wrapped in `{ …; } 2>&1 | tee >(pbcopy)` like every other command — the browser/passkey flow and the 2FA prompt reach the terminal through the pipe (s117). The check confirms the sign-in; it does not decide whether to do it. Skipped, an unauthenticated `npm publish` fails as **404 Not Found**, not "please sign in" (E401 masking as E404).
2. Bump `version` in `npm/package.json` and `pip/pyproject.toml` + `pip/src/allostatik/__init__.py` (keep them in lockstep).
3. **Write the `CHANGELOG.md` entry** — headed `## X.Y.Z — date — <two-word title>` with **Tag:** `vX.Y.Z`, then *What's new* (three to five short lines), *Why it's worth it* (one paragraph), *What it costs* (see below), *To upgrade* (the prompt to paste, or a pointer to the bootstrap one). **Voice: an App Store "What's New" note** — plain, benefit-led, readable by someone who has never opened the repo; no region names, hashes, or internals — those live in `UPGRADING.md`. Exemplars: Apple's and Instagram's update descriptions. The suite refuses a head entry whose version doesn't match the package.
    - **Cost, not wall-clock.** *Takes about N minutes* was the old slot and it measured the wrong resource — the s107 adopter run spent its attention, not its clock, and said so. State the shape of the cost instead: it is front-loaded and near-fixed, so a small release is its worst case. Any number here is one this release actually counted; leave it out otherwise, because a borrowed estimate is the most concrete-sounding sentence in the entry and the one most likely to be wrong.
    - **If this release relocates anything, ship the list.** An upgrade may only write inside the stamped regions, so it cannot correct an adopter's own files. After 0.3.5 moved where session entries live, installs went on carrying instructions that named no file, silently. The release owes them **a list, not an edit**: name the files a relocation leaves reading false, put them in the entry, and say plainly that fixing them is theirs to do. Build the list, never type it: `grep -rn '<the old name or path>' templates/project-boilerplate/` gives every adopter-owned template file that still points at what moved, and an install may carry more, so offer it as a starting point rather than a guarantee. Ask the question every release. When nothing moved, say so in the release commit message and leave the entry alone — the adopter needs a list, not a reassurance.
4. **Restamp and verify.** `scripts/stamp-regions.py --write` — always, because the stamps carry the version you just bumped (and the new hash, if Part 1 of the template `workflow.md` or the `CLAUDE.md` / `AGENTS.md` fences changed); then `scripts/stamp-regions.py` (verify) and `scripts/test-installers.sh` — both must pass.
5. `scripts/bundle-templates.sh` (refreshes the bundled fallback from `templates/`).
6. **Commit, tag, push the tag, upgrade the flagship, publish from the tag, push `main` — in that order.** Commit with an explicit file list. `git tag -a vX.Y.Z -m "X.Y.Z"`, then `git push origin vX.Y.Z` and confirm it with `git ls-remote --tags origin vX.Y.Z`. Then upgrade the flagship (`allostatik-dev`) through the routine at that tag — the release's first real run, before any adopter can install it. A defect found here costs a patch tag, never a republish. Then publish **from the tag checkout**, so the package's `gitHead` is the tag's commit even when a fix has landed on `main` in between. The command: `git checkout -q vX.Y.Z && (cd installers/npm && npm publish) && (cd installers/pip && rm -rf dist && python3 -m build && uvx twine upload dist/*); git checkout -q main`. (At 0.3.5 the flagship run found a suite bug, and its fix sat on `main` between tag and publish.) Run `npm publish` bare — no pipe, no `tee`, no `--otp` placeholder — because npm asks for the 2FA one-time code (`EOTP`) and can only prompt with a terminal on stdout. `python3 -m build` because macOS ships no `python` shim, and `uvx twine` because it ships no `twine` on PATH either. `python3 -m twine` needs twine pip-installed first and is the fallback, not the default. `rm -rf dist` keeps stale artifacts out of the upload. Then `git push origin main`. The upgrade routine's cross-check compares `gitHead` with the commit the tag resolves to, so a package published from `main` after any post-tag commit halts every adopter's upgrade.
7. **Confirm from the outside.** From a second machine when one is at hand. `git ls-remote --tags origin` shows the tag, `npm view allostatik version gitHead` names the tag's commit, and `python3 -m pip index versions allostatik` (or the PyPI page) lists the version. Report the release as done only after those reads.

Online installs always get current `main` automatically; the bundled fallback advances only via republish — so republish after significant template changes to keep offline installs close. `init.sh` and the repo always carry current `main`. **Upgrades** are different: they fetch the release tag named in `CHANGELOG.md`, never `main` — a template fix reaches existing installs only when it's released, which is the point.

*Queued (s95): `scripts/release.sh <version>` — the ritual above as one script with the sign-in gate, lockstep bump, changelog-head check, stamp verify, suite, bundle, commit, tag, publish, push. The 0.3.4 release was the last by-hand run; whatever it fumbled is that script's spec.*
